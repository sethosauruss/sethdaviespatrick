Cybersecurity Home Lab

In progress Built and running. Attack testing is the current phase.

A self-built home lab simulating a small-scale enterprise IT environment, focused on infrastructure security, system administration and defensive cybersecurity.

What is built

Rack
A Tecmojo 6U, 10 inch rack, fully assembled. From the top down: pfSense firewall (an HP EliteDesk 800 G3 Mini) at 6U, the Proxmox host (a second EliteDesk) at 5U, a patch panel and brush panel at 4U, the TL-SG108E switch and a JetKVM at 3U, the Raspberry Pi 5 shelf at 2U, and 1U spare.
Cabling
A 12-port patch panel, wired and labelled. Cables are colour-coded by zone: green for Trusted, blue for Lab, orange for IoT/DMZ and grey for the uplink.
Firewall
pfSense 2.7.2 with router-on-a-stick off one onboard network port. I dropped a USB ethernet adapter after it proved unreliable.
DNS and remote access
DNS runs on Unbound, access-listed per subnet. Remote access is through Tailscale (on the Pi and my PC). No ports are forwarded except a Plex forward restricted to a source.
Raspberry Pi 5Trusted VLAN
Raspberry Pi OS Lite with Docker Compose, running Plex (read-only media mounts), Samba (two shares only), Tailscale, Vaultwarden (backup tested), Uptime Kuma and Seerr. Seerr is for requests and discovery only, because I am deliberately not building a full download-automation stack. SSH is hardened: key-only, set in a drop-in config and verified with sshd -T.
Proxmox hostManagement VLAN
Proxmox VE 9 with hardened SSH, verified both ways: the key works and a forced password login is correctly refused. It hosts a Kali VM and a DVWA target VM, both on the Lab VLAN. Kali has a clean-install snapshot. DVWA runs on Debian 13 with Apache, PHP and MariaDB, with clean-install, dvwa-ready and attack-baseline snapshots.
JetKVMManagement VLAN
Out-of-band console and BIOS access to the machines in the rack.

Network zones

  • VLAN 10 Trusted: everyday devices and the Raspberry Pi.
  • VLAN 20 Lab: the Kali and DVWA VMs, kept away from everything else.
  • VLAN 30 IoT/DMZ: smart and low-trust devices.
  • VLAN 99 Management: the Proxmox host and the JetKVM.

There is also the LAN on VLAN 1 and the WAN on VLAN 2. Every zone is firewalled default-deny. I tested the isolation two ways: through the firewall rules, and with an 802.1Q audit of the switch, which caught and fixed a couple of leftover VLAN memberships.

Attack testing (current phase)

DVWA login page
I brute-forced the main login page. A CSRF token and redirect caused false positives, so I wrote a custom curl loop that fetches a fresh token for every attempt and follows redirects. It found the default credential cleanly.
DVWA Brute Force module
I used Hydra against the separate training module (a GET form with no CSRF at the Low level). Fixing a field-ordering mistake and a typo that caused a false positive got the same credential. Both results were checked by hand in the browser.

Known gaps

  • No SIEM or detection layer yet. Wazuh is the long-standing gap.
  • Backups are patchy. Only Vaultwarden has a proper backup script so far.

Planned, not started

More targets
Metasploitable2 for a broader attack surface and Metasploit practice, OWASP Juice Shop as a more realistic modern web app, and re-running the brute-force tests at DVWA Medium and High difficulty.
More attack tooling
Running the next DVWA rounds (SQL injection, XSS, command injection) through Burp Suite, and CALDERA and Atomic Red Team for automated adversary emulation mapped to MITRE ATT&CK.
Detection
Wazuh, possibly paired with the pfSense packages pfBlockerNG (reputation and GeoIP blocking) and Suricata or Snort (IDS/IPS).
Documentation tooling
NetBox for IPAM and DCIM, replacing the markdown VLAN and rack tables with a queryable system.
Second Raspberry Pi 5 (8GB)

1U rack display

Backups

Traffic visibility
